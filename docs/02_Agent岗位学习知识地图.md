# Agent 岗位学习知识地图

> 目标：从“能调用大模型 API”进阶到“能交付可靠、可评测、可运维的 Agent 系统”。本文按必须掌握、需要熟悉、进阶方向组织，并给出记忆清单与练习路径。

## 1. 首先建立正确认知

**Agent = LLM + 状态 + 工具 + 控制循环 + 反馈/评测。**

它不是一个 Prompt，也不等于 RAG。RAG 解决“取到外部知识”；工具调用解决“执行动作”；Agent 负责决定何时检索、何时调用工具、何时停止、如何处理失败与把结果交给用户。

面试时应能清楚区分：

| 概念 | 核心问题 | 典型产物 |
|---|---|---|
| Prompt Engineering | 如何稳定引导模型 | system prompt、示例、输出约束 |
| RAG | 如何基于外部知识回答 | chunk、embedding、召回、重排、引用 |
| Tool Calling | 如何让模型调用受控能力 | JSON Schema、服务端工具执行 |
| Agent | 如何多步规划与执行 | 循环、状态、停止条件、错误恢复 |
| Workflow | 如何让固定流程稳定执行 | DAG、状态机、审批节点 |

经验法则：**流程确定时优先 Workflow；任务开放、需要动态选择工具时才使用 Agent。**

## 2. 必须掌握：LLM 基础

### 2.1 Transformer 与生成

需要能解释而不必手推全部公式：

- Tokenization：模型按 token 而非汉字/单词计费和受上下文限制。
- Context window：历史、系统提示、工具结果、RAG 片段共同占用窗口。
- Temperature / top-p：控制采样随机性；事实型任务通常低温度。
- System / User / Assistant / Tool 消息：角色和消息顺序影响模型行为。
- 幻觉：模型生成“看起来合理”的内容，不代表事实；需要 grounding、验证和约束。

必须记住：模型输出是概率生成，不是数据库查询；“要求模型不要幻觉”不足以解决幻觉。

### 2.2 Prompt 设计

掌握以下模板要素：

1. 角色与任务边界。
2. 可用资料/工具及禁止事项。
3. 输出格式（JSON、表格、引用格式）。
4. 资料不足时的行为。
5. 少量高质量示例（few-shot）。

常见失败与改法：

- Prompt 过长：压缩规则、检索更少更准的上下文。
- 输出不稳定：结构化输出/JSON Schema、低温度、校验与重试。
- 资料未被使用：把来源和引用要求写入 Prompt，且后端做校验。
- 指令注入：将检索文档当作“不可信数据”，明确禁止文档内容改变系统规则。

## 3. 必须掌握：RAG 全链路

### 3.1 文档处理

学习顺序：提取文本 → 清洗 → 分块 → 元数据 → 索引。

- 结构化切块：按标题/段落/列表/表格优先，再对长段做窗口切分。
- Overlap：缓解跨块信息截断，但过大会引入重复与成本。
- 元数据：文档名、页码、标题、更新时间、权限、任务/租户 ID。
- 多格式：PDF 文本层、扫描 OCR、DOCX 表格、HTML 噪声、CSV 行语义。

### 3.2 检索与重排

必须说清各组件的价值：

- BM25：术语精确匹配、可解释、无需模型；弱于语义近义表达。
- Embedding：语义相似；受模型、领域、向量维度和切块质量影响。
- 向量库：相似度搜索、过滤、持久化；常见 Chroma、FAISS、Milvus、pgvector。
- Hybrid search：融合 BM25 与向量，生产常用。
- RRF：按名次而不是原始分数融合异构检索器，常见形式 `score(d)=Σ 1/(k+rank_i(d))`。
- Reranker：CrossEncoder 直接判断“query-片段”相关性，慢但精，适合对少量候选精排。

### 3.3 RAG 评测

必须会算/解释：

- Recall@K：正确证据是否在前 K；低说明召回有问题。
- Precision@K：前 K 噪声比例；低说明上下文污染。
- MRR：第一个正确证据的平均倒数排名；衡量排序质量。
- Faithfulness/Groundedness：回答是否由证据支持。
- Answer Correctness：回答是否满足标准答案。
- Latency、Token cost：线上可用性指标。

不要只看“模型感觉回答不错”。先定位问题在**解析、切块、召回、重排还是生成**，再调参。

## 4. 必须掌握：工具调用与 Agent 控制

### 4.1 Tool/Function Calling

- 用 JSON Schema 描述工具名称、用途、参数、必填字段。
- 模型只提出调用意图；真正执行必须在服务端。
- 对每个参数做类型、长度、权限和业务校验。
- 工具结果作为 `tool` 消息回填模型，而非拼成不受控自然语言。
- 工具白名单、超时、重试、幂等、审计日志不可省略。

### 4.2 常见循环

```text
用户问题 → LLM 决策 → 工具调用 → 服务端校验/执行 → 工具结果 → LLM 最终回答
```

要实现：

- 最大步数，防止无限循环；
- 工具调用失败后的可读降级；
- 重复调用检测；
- 每步 trace；
- 明确停止条件；
- 工具输出大小限制，避免 context 爆炸。

### 4.3 ReAct、Plan-and-Execute、状态机

- ReAct：思考/动作/观察交替；便于动态探索，但轨迹可能长且不稳定。
- Plan-and-Execute：先产出计划，再执行；适合多子任务，但计划可能过度复杂。
- 状态机/图：显式定义节点与转移；生产稳定性、可恢复性更好。

关键观点：不要暴露或依赖模型的私有思维链；对用户展示的是可审计的“工具轨迹、来源和结果摘要”。

## 5. 必须掌握：记忆、会话与上下文

- 短期记忆：最近消息窗口；控制 token 长度。
- 长期记忆：用户偏好、事实、任务状态；需要检索、时间戳、权限与可删除能力。
- 摘要记忆：把早期对话压缩为摘要；必须保留关键信息来源。
- 会话隔离：`session_id` 不足，还需 `user_id/tenant_id/task_id`。
- 上下文选择：不是“把全部历史塞给模型”，而是根据问题选择相关历史和资料。

## 6. 必须掌握：安全、可靠性与成本

### 安全

- Prompt injection / indirect prompt injection：文档可能包含“忽略之前指令”等恶意内容。
- 数据越权：RAG 查询必须做租户、用户、文档权限过滤。
- 工具越权：工具权限不由模型决定，而由服务端身份和策略决定。
- PII/敏感数据：脱敏、访问日志、保留期限、删除能力。
- 密钥：只存服务端环境变量或密钥管理服务，不能进入前端或 Git。

### 可靠性

- 超时、重试、指数退避、熔断、降级。
- 模型/向量库不可用时的行为必须清晰。
- 异步任务要可查询状态、可重试、可幂等。
- 外部副作用工具（发邮件、下单）需要人工确认与幂等键。

### 成本与性能

- 监控 prompt/completion token、调用次数、缓存命中率。
- 使用小模型做分类、改写、抽取；大模型做复杂生成。
- Embedding 批处理，缓存检索与模型结果。
- 控制 top-k、重排候选数、历史窗口和最大 Agent 步数。

## 7. 需要熟悉：工程化工具

- Python：asyncio、类型标注、pytest、httpx、日志、异常处理。
- Web：HTTP、REST、SSE、WebSocket、鉴权、中间件、CORS。
- 数据库：SQL、索引、事务、连接池、迁移；SQLite 与 PostgreSQL 的边界。
- 队列：Celery/RQ/Arq、Redis、死信队列、重试、幂等。
- 部署：Docker、环境变量、Nginx、CI/CD、健康检查。
- 可观测性：结构化日志、trace ID、OpenTelemetry、Prometheus/Grafana、错误追踪。
- 框架：理解 LangChain/LangGraph、LlamaIndex、Semantic Kernel 的思想即可；先能手写简单循环，再使用框架。

## 8. 建议的 12 周学习路径

| 阶段 | 目标 | 输出作品 |
|---|---|---|
| 1-2 周 | Python、HTTP、LLM API、Prompt | 一个结构化输出聊天 API |
| 3-4 周 | 文档解析、Embedding、向量库、BM25 | 可引用的基础 RAG |
| 5-6 周 | 混合检索、reranker、评测集 | Recall@K/MRR 报告 |
| 7-8 周 | Tool Calling、Agent 循环、SSE | 多工具流式 Agent |
| 9-10 周 | 会话、权限、限流、队列 | 可登录/隔离的企业原型 |
| 11-12 周 | Docker、监控、压测、CI | 可部署项目与技术复盘 |

## 9. 面试前必须能回答的问题

1. 为什么只用向量检索不够？BM25、Hybrid、RRF、reranker 分别解决什么问题？
2. 切块大小和 overlap 如何影响 Recall、上下文噪声和成本？
3. 如何证明回答基于资料，而不是模型幻觉？
4. Tool Calling 与让模型输出一段“调用指令文本”相比为什么更安全？
5. Agent 为什么需要最大步数、超时、幂等和人工审批？
6. 怎样防止 RAG 跨租户泄露资料？
7. 如何评测 RAG，而不是只靠人工主观体验？
8. SSE 与 WebSocket 有何区别，聊天为何常用 SSE？
9. 如何降低 Agent 成本与延迟？
10. 线上模型或向量库故障时，系统怎样降级？

## 10. 记忆卡片

- **RAG 的瓶颈常在检索，不在模型。**
- **向量相似不等于事实支持，引用与评测不可少。**
- **模型决定“想调用什么”，服务端决定“是否允许执行”。**
- **确定性流程优先 Workflow，开放任务才使用 Agent。**
- **所有外部输入，包括上传文档，都可能是不可信的。**
- **先用评测定位问题，再调 Prompt、chunk 或模型。**
- **生产 Agent 的核心竞争力是可靠性、权限、观测与成本控制。**
